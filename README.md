# Floral Recipe & Cost Management App

A Flask-based web application designed for retail florists to manage stem inventory, construct arrangement recipes, automatically calculate wholesale costs, apply category markups and labor fees, and generate suggested retail prices (SRP).

The application supports florist workspaces with separate users, inventory, products, recipes, and subscription status.

---

## 🛠️ Tech Stack

* **Backend:** Python 3.12, Flask, Flask-SQLAlchemy (SQLite locally; PostgreSQL in production)
* **Frontend:** Jinja2 Templates, Vanilla JavaScript, Tom-Select (Searchable Dropdowns)
* **Styling:** SCSS source with checked-in compiled CSS

---

## 🗄️ Database Architecture

Every florist-owned record has a `workspace_id`; database relationships and route queries are scoped to the logged-in user's workspace. Billing belongs to a workspace so staff accounts can be added later without changing ownership. The core models are:

1. **`Workspace`**: One florist business and its owned data.
2. **`User`**: Email, password hash, and workspace-scoped `admin` or `user` access.
3. **`UserInvitation`**: A single-use, seven-day invitation link for a workspace member.
4. **`Subscription`**: Workspace billing status and Stripe identifiers.
5. **`Vendor`**: Supplier information (`id`, `workspace_id`, `name`).
6. **`IngredientType`**: Category markups (`id`, `workspace_id`, `name`, `markup` multiplier).
7. **`DesignType`**: Labor/design style fees (`id`, `workspace_id`, `name`, `design_fee_percentage`).
8. **`Ingredient`**: Stems and supplies scoped to a workspace, type, and optional vendor; ingredient photos are stored under `instance/ingredient-uploads/`.
   * *Calculated:* Unit Cost = `cost_per_pkg / qty_per_pkg`
9. **`Product`**: Arrangement bases scoped to a workspace and design type.
   * *Calculated Metrics:* Raw Wholesale Cost, Marked-Up Cost, Design Fee, Suggested Retail Price (SRP), Profit Margin %.
10. **`ProductIngredient`**: Workspace-scoped product recipe rows.

## Team access, recipe library, and exports

Workspace owners can open **Team Access** to create an invitation link and choose either **Admin** or **User** access. Share the generated link directly with the invitee; it can be used once and expires after seven days. The app does not currently send invitation email. Admins can change a member's access level at any time, and a workspace must retain at least one admin.

Users (designers and sales associates) can view the recipe library and use the separate Quick Calculator page. The recipe library omits costs and prices; the user calculator shows ingredient names and a suggested retail price only. Ingredient, vendor, product editing, reports, exports, and billing are restricted to admins.

Admin data pages include Excel downloads. The Products & Recipes workbook contains product pricing and a separate recipe sheet. The Ingredients page accepts `.xlsx` uploads with **Name**, **Category**, **Package Cost**, and **Quantity per Package** columns; **Vendor** is optional. Category and vendor names must already exist in the workspace. Ingredient names are compared without case sensitivity; existing names are skipped. Invalid rows prevent the workbook from importing any new ingredients.

Vendor inventory reports include ingredient photos and can be printed or downloaded as Excel. Uploaded ingredient images are limited to 5 MB and supported image types. In production, mount `instance/ingredient-uploads/` on persistent storage and include it in backups; local instance storage is not shared across application replicas.

## Running locally

Use Python 3.12 and install the dependencies. The checked-in example uses a local SQLite database, so you don't need to create a hosted database just to run it:

```sh
python -m venv .venv
. .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
```

Replace `SECRET_KEY` in the untracked `.env` file with a random value generated by:

```sh
python -c 'import secrets; print(secrets.token_hex(32))'
```

Then create the local database schema and start the development server:

```sh
flask --app app db upgrade
flask --app app run --debug
```

Flask reads `.env` when running these commands. `DATABASE_URL=sqlite:///app.db` creates the local database under Flask's `instance/` folder. `.env` is ignored by Git; do not commit it or paste its secrets into chat. The app requires a configured `SECRET_KEY`.

New accounts start with their own empty workspace and default flower/design categories. Signup uses email and a password (minimum 12 characters); it does not import the removed personal spreadsheets. Run database migrations before starting the server; the app intentionally does not create or alter production tables at startup. Until you configure Stripe test credentials below, new workspaces will see a billing-not-configured notice and can't enter management pages.

The app serves the checked-in `static/css/main.css` directly; it does not compile SCSS at runtime.

## Stripe subscriptions

For local payment testing, create a Stripe account in test mode, create a recurring Price, then add these test credentials to `.env`:

```text
STRIPE_SECRET_KEY
STRIPE_PRICE_ID
STRIPE_WEBHOOK_SECRET
```

For local webhook delivery, install and run the Stripe CLI, then start forwarding events to `http://127.0.0.1:5000/billing/webhook`; use the `whsec_...` signing secret it prints as `STRIPE_WEBHOOK_SECRET`. Subscribe to:

```sh
stripe listen --forward-to localhost:5000/billing/webhook
```

For deployment, set the webhook endpoint to `https://<your-domain>/billing/webhook` and subscribe to:

* `checkout.session.completed`
* `customer.subscription.created`
* `customer.subscription.updated`
* `customer.subscription.deleted`

Checkout activation and cancellation are driven by signed webhook events, not by the browser's success redirect. The billing portal is used for payment method and cancellation management. Use HTTPS and test-mode Stripe credentials before enabling live billing.

## Deployment checklist

* Set a strong, stable `SECRET_KEY`, `SESSION_COOKIE_SECURE=1`, and a production database URL. PostgreSQL is recommended for multi-instance deployments; the single-instance PythonAnywhere example below uses SQLite.
* Keep Stripe credentials in the hosting provider's secret manager.
* Run `flask --app app db upgrade` during deployment and configure database backups.
* Serve behind HTTPS using Gunicorn (for example `gunicorn app:app`).
* Configure Stripe webhook delivery and test signup, payment, cancellation, and tenant isolation before launch.

## Deploying on PythonAnywhere

These steps describe a single-instance deployment. Confirm that your PythonAnywhere account supports the Python version and outbound connections your app needs; Stripe billing also needs a public HTTPS site and a reachable webhook endpoint.

1. In a PythonAnywhere **Bash console**, clone the repository and create a virtual environment using a Python version supported by your account:

   ```sh
   git clone <your-repository-url> ~/floral-recipe-app-saas
   cd ~/floral-recipe-app-saas
   mkvirtualenv --python=/usr/bin/python3.12 floral-recipe-app
   pip install -r requirements.txt
   mkdir -p instance/ingredient-uploads
   ```

   If Python 3.12 is not available for your account, select an available version supported by the dependencies and update the virtualenv path/version accordingly.

2. Generate a secret key in the console:

   ```sh
   python -c 'import secrets; print(secrets.token_hex(32))'
   ```

   Keep the value private and stable across restarts. For this single-instance example, SQLite stores data under the project `instance/` directory, which must remain on persistent storage. Back up both `instance/app.db` and `instance/ingredient-uploads/`. For a multi-instance or higher-availability deployment, configure a supported shared database and persistent file storage instead.

3. In the PythonAnywhere **Web** tab, create a **Manual configuration** web app with the same Python version as the virtualenv. Set the source code and working directory to `/home/<your-username>/floral-recipe-app-saas`, and set the virtualenv to `/home/<your-username>/.virtualenvs/floral-recipe-app`. Add the static file mapping `/static/` to `/home/<your-username>/floral-recipe-app-saas/static`.

4. Edit the WSGI configuration file linked from the Web tab. Set the environment before importing the Flask application (replace the username and generated key):

   ```python
   import os
   import sys

   project_home = "/home/<your-username>/floral-recipe-app-saas"
   if project_home not in sys.path:
       sys.path.insert(0, project_home)

   os.environ["SECRET_KEY"] = "<your-generated-secret>"
   os.environ["DATABASE_URL"] = (
       "sqlite:////home/<your-username>/floral-recipe-app-saas/instance/app.db"
   )
   os.environ["SESSION_COOKIE_SECURE"] = "1"

   from app import app as application
   ```

   Do not commit this WSGI file or secret to the repository. The WSGI process does not automatically read the project's `.env` file. If enabling Stripe, set `STRIPE_SECRET_KEY`, `STRIPE_PRICE_ID`, and `STRIPE_WEBHOOK_SECRET` in this same environment before importing `app`.

5. Before serving the site, run the migrations from a Bash console with the virtualenv active and the same settings used by WSGI:

   ```sh
   cd ~/floral-recipe-app-saas
   export SECRET_KEY='<the-same-generated-secret>'
   export DATABASE_URL='sqlite:////home/<your-username>/floral-recipe-app-saas/instance/app.db'
   export SESSION_COOKIE_SECURE=1
   flask --app app db upgrade
   ```

6. In the Web tab, configure HTTPS, then click **Reload**. Test signup, admin and user logins, account switching, image uploads, and workspace access. For Stripe, configure `https://<your-domain>/billing/webhook` in Stripe and subscribe to the webhook events listed above. Use Stripe test credentials first.

This is a first subscription foundation: production launch should also include email verification, password reset email delivery, rate limiting, operational monitoring, and a tested data migration/backup plan for any old personal database.
